# 更新说明

本项目的脚本更新说明统一写在 Markdown 里，一个版本一节，倒序排列（最新在最上面）。
 
## 书写约定

- **一节 = 一次发布**：标题为 `## v<版本号> · <YYYY-MM-DD>`，版本号取根目录 `microsoft-rewards.user.js` 的 `@version`。
- **必须写清四件事**：改了什么、为什么改（线上现象/根因）、影响哪些文件、怎么验证改对了。
- **面向"跑的人"**：写的是「下次看日志该看哪一行」，不是代码 diff。
- **文件指纹**用 `md5sum`（前 8 位即可）+ 行数，方便上传后核对是不是同一份。
- 只影响 `zy.py` / `sc_deploy.py`、没动脚本本体时，用 `## v<版本号> · <日期>（仅 zy.py / sc_deploy.py）`。

## v1.0.1 · 2026-11-24（仅 zy.py：时段默认对齐脚本、收工时间说话、完成即关）

这一节只动 `zy.py`（4903 行，MD5 `c156f95d`），脚本本体仍是 1.0.1（11358 行 / `86ecf515`）。

### 改了什么

**① `RUN_WINDOW` 默认 09:00-15:00 → 09:00-23:00**

和脚本的 `Config.winTime`（默认 09:00~23:00）对齐。原来两边不一致：脚本能跑到 23:00，
`zy.py` 却认为 15:00 之后就算「不在时段」，只能靠 `RUN_LATE_EXTEND` 顺延，日志一行
`已过运行时段 09:00-15:00，收工时刻 18:00` 就是这么来的。

**② 收工时间说话：`RUN_DEADLINE` 默认留空 = 取时段末点**

`RUN_DEADLINE` 从写死 `18:00` 改成默认留空；留空时取 `RUN_WINDOW` 最后一段的末点
（09:00-23:00 → **23:00**），日志会打 `⏰ 未配 RUN_DEADLINE → 收工时刻取运行时段末点 23:00`。
想更早收工再显式配（如 `RUN_DEADLINE=21:30`）。

**③ `BING_RUN_SECONDS` 靠边：默认 0，不再参与计时**

运行时长一律由 `收工时间 - 现在` 算出来，日志是
`⏰ 运行时长由收工时间 23:00 决定：13小时55分`（不再带「原 BING_RUN_SECONDS=36000」这种
永远不生效的尾巴）。它只剩一个用途：`RUN_WINDOW` 留空 + 没配 `RUN_DEADLINE` 时的兜底，
此时 0 = 常驻，等全部账号报完成才结束。启动日志也会打出实际取值和来源（面板/默认）。

**④ 完成即关，加了总开关**

以前「账号完成 → 关它自己的浏览器」只在两处触发（QLREPORT-END 达标 / 「今日所选任务已全部
完成…休眠」）。现在把触发点和行为都写明，并加 `SC_CLOSE_ON_DONE`（默认 1）：

- 日志从「✅ 账号 X 任务全部完成，关闭浏览器」改成带原因的
  `✅ 账号 X 任务全部完成（达标） → 关闭它的浏览器` / `✅ 账号 X 今日无待办（休眠） → 关闭它的浏览器`；
- 全部账号关完会打 `🎉 全部账号任务已完成，提前结束` 并立刻收尾，不等收工时刻；
- `SC_CLOSE_ON_DONE=0` → 单账号完成时不立刻关（留到全部完成后的收尾），排查用。

### 怎么验证改对了

启动头四行应该是：

```
  BING_RUN_SECONDS = 0（默认）：由收工时间决定实际时长
  RUN_WINDOW = 09:00-23:00  RUN_DEADLINE = 取时段末点  RUN_MIN_SECONDS = 3小时0分
⏰ 未配 RUN_DEADLINE → 收工时刻取运行时段末点 23:00，运行时长由它决定
⏰ 运行时长由收工时间 23:00 决定：13小时55分
```

跑起来以后，某个账号先完成时应该看到（不用等收工）：

```
✅ 账号 long 任务全部完成（达标） → 关闭它的浏览器（先等 20 秒让脚本收尾）
```

五个都完成时：`🎉 全部账号任务已完成，提前结束` + `🚪 任务结束，正在关闭全部浏览器...`。

### 追加：零输出止损 `SC_IDLE_CLOSE_MIN`（默认关闭）

**为什么加**：能被「完成即关」带走的只有会报完成的账号。报不出来的（桌面任务缺 Chrome、
国际版活动没下发 hash、Cookie 掉登录……）没有任何信号，浏览器就一直挂到收工 ——
收工时间现在是 23:00，等于一天有十几个小时的常驻 Chromium，5 个账号就是 5 个。
`STALL_ALERT_MIN`（40 分钟）那条只会「试着救」（reload 扩展），救不活就天天告警、浏览器照挂。

**怎么算的**：巡检（每 2 分钟一次）里新增第 ③ 项检查 ——
连续 `SC_IDLE_CLOSE_MIN` 分钟一条脚本日志都没有，就关掉这个账号的浏览器。
基准点取「最近一条日志」，从没出过声的账号取「浏览器启动时刻」。
默认 **0 = 不启用**，行为与以前完全一致。

```
SC_IDLE_CLOSE_MIN = 120     # 想省资源就配这个；要明显大于 STALL_ALERT_MIN(40)
```

配得太小会踩坑（自动修复还没试完浏览器就被关），所以启动时会自检并在日志里提醒：

```
  SC_IDLE_CLOSE_MIN = 120 分钟（连续这么久零脚本日志就关掉该账号浏览器）
⚠️ SC_IDLE_CLOSE_MIN(30) ≤ STALL_ALERT_MIN(40)：自动修复还没试完就会把浏览器关掉，建议设成 80 以上
```

**止损时会发生什么**：

- 该账号按「未完成」收尾，**其余账号照跑**（不触发提前结束，除非所有账号都已收尾）；
- 关掉的浏览器不受 `SC_CLOSE_ON_DONE=0` 影响（止损就是要关）；
- 面板日志两行：先 `🧹 账号 X 已 N 分钟没有任何脚本日志（阈值 M 分钟）→ 关闭它的浏览器省资源`，
  再 `✅ 账号 X 长时间无输出（N 分钟） → 关闭它的浏览器`；
- 通知标题是「【账号止损】X 长时间无输出」，措辞不会说成「任务已完成」；
- 全部账号都收尾时，汇总如实分开：`⚠️ 1/2 个账号长时间没有输出，已关闭浏览器；其余已完成。`，
  明细里对应账号写 `⚠️ 长时间没有脚本日志，已关闭浏览器（未确认完成）`。

### 上线注意

只要换 `zy.py`（`4903 行 / c156f95d`）。脚本本体不用动，商店线上 1.0.1 即可；
`runUntil` 那条通道要 1.0.1 才认，两边都到位才会出现 `🕘 运行时段由 zy.py 接管`。
零输出止损是**可选**的：不配 `SC_IDLE_CLOSE_MIN` 就完全按老行为走（浏览器挂到收工）。

## v1.0.1 · 2026-11-23（运行时段交给 zy.py 定，脚本不再和面板各算一套钟）

### 现象（2026-11-23 23:33 那次运行的日志）

五个账号在 23:34:53~57 全部升到 1.0.0，`install success` 一个不缺；然后 23:40 第一次
cron 唤醒，五个账号**整齐划一地什么都不干**：

```
[23:40:00] [long] [info] 🔄 检测到底座切换（ref8787-1.0.0），已重置跨版本的完成标记
[23:40:00] [long] [info] 🧹 运行时段结束：已清理 3 项运行缓存（今日进度保留）
[23:40:01] [long] [info] 🌙 当前不在运行时段（09:00~23:00，以面板 Config.winTime 为准），本次唤醒不跑任务
```

zy.py 那边同时还在 `⏳ 保持浏览器运行 1532 秒`，一直等到 23:59 关浏览器 —— 25 分钟全程空转，
当天 0 产出。

### 根因：两套时钟，谁也不知道对方

- zy.py 的作息：面板 23:33 才把它拉起（正常应 09:00），`RUN_WINDOW=09:00-15:00` 早过了 →
  按「跑完再结束」把收工顺延到 23:59，于是它认为「现在开着工，脚本该干活」。
- 脚本的作息：`@crontab */20` 唤醒后只认**自己的** `Config.winTime`（默认 09:00~23:00）→
  23:40 已经出窗 → 一行 🌙 就返回。
- 两者之间**没有任何通信**，全靠人去把两边配置调成一样。只要出现「面板起晚 / 手动重启 /
  某天顺延」，两个时段必然错位，而且错位时脚本不会报错，只会安静地不干活。

### 改了什么：把「几点开机、几点收工」的唯一决定权交给 zy.py

- **zy.py 发时段**：`write_run_plan()` 把收工时刻记进全局 `_RUN_UNTIL_MS`，
  随 `/zy-ports.json` 一起发出去（新增顶层字段 `runUntil`，epoch 毫秒）；
  计划日志多一句 `🕘 已同步给脚本（端口表 runUntil=23:59，脚本不再看面板 winTime）`。
- **脚本接时段**：`PortResolver` 抓端口表时顺手记下 `runUntil`（只认「未来 26 小时内」的值，
  过期/脏值一律不认，免得被错误时钟锁在时段外一整天）；`Sched.inWindow()` 先看它，
  没有才回落面板 `Config.winTime` —— **脱离容器单独用时行为完全不变**。
- **只在会被拦下时才去问**：闸门里先按面板判断，只有「面板说不该跑」才现抓一次端口表
  （2.5 秒超时），所以正常情况下不多花一次请求。
- **顺手修掉自相矛盾的两条告警**：原来「收工顺延到 23:59」下一行紧接
  「按 23:59 准点收工，不做顺延」（一条是顺延分支打的，一条是 `_finish()` 打的），
  读日志的人会以为程序在抽风。现在顺延过就不再喊「不做顺延」，改成一条有信息量的预警：
  `⏰ 实际可用仅 25分33秒，不足脚本一轮的硬上限 40分（20 分钟预算 + 20 分钟收尾）：即使开跑也大概率跑不完`。

### 影响文件

| 文件 | 行数 | MD5 | 是否需重新上传 |
|---|---|---|---|
| `microsoft-rewards.user.js` | 11358 | `86ecf515` | **是**（1.0.0 → 1.0.1，要发商店） |
| `tools/zy.py` | 4780 | `a93cef35` | **是**（容器里的文件替换掉；同日又改了一版，最新指纹见上一节） |

两边**都要换**：只换脚本、zy.py 仍发不带 `runUntil` 的端口表 → 脚本回落面板 winTime，
行为和 1.0.0 一样；只换 zy.py、脚本仍是 1.0.0 → 面板 winTime 照样拦，一样空转。

### 怎么验证改对了

容器日志按顺序应该出现这几行（不再有 `🌙 当前不在运行时段`）：

```
📋 任务计划：开机 09:00，收工 23:00；…；🕘 已同步给脚本（端口表 runUntil=23:00，脚本不再看面板 winTime）
🗺️ 端口表批量预发布完成：5/5 个账号
🕘 运行时段由 zy.py 接管：收工 23:00（面板 winTime 本次不生效，容器里作息以 zy.py 为准）
🕘 本轮生效时段：…，当前在时段内
▶️ 本轮进入执行流程
```

- 白天（面板 winTime 本来就在窗内）**不会**出现「由 zy.py 接管」那行 —— 只有出窗时才打，属正常。
- 收工时刻到了以后脚本自动回落到面板 winTime，不会因为 `runUntil` 没清掉而整夜跑。

## v1.0.0 · 2026-11-23（仅 zy.py · 配套新版脚本：端口表批量预发布 / 浏览器寿命校验 / 停摆阈值按 20 分钟节拍）

这一节只动 `zy.py`（4750 行，MD5 `a614cf73`）；脚本本体除元数据里的主页地址外没有改动
（11301 行，MD5 `17247720`）。换底座之后，脚本的节拍从「每分钟敲门」
变成「每 20 分钟跑一轮」，`zy.py` 里三处按旧节拍写的假定必须跟着改，否则换版当天就会踩坑。

### 现象（换版前那些日志里的老毛病）

joe 那台的第一轮，脚本报的是认领失败：

```
🔴 认领端口：端口表里没有本机 MUID（8f3c…）→ zy.py 还没发布这台浏览器，本轮用兜底端口
🟡 本轮使用兜底端口：9222（多账号会串号）
```

兜底端口就是 9222 —— 也就是 long 那台。于是这一轮 joe 的读积分、点任务全打在 long 身上。
joe 还有更典型的一次：浏览器被「已在运行，本次沿用」捡起来，端口也认领到了，
但登录态早已失效 —— 脚本能开门，读不到账号。

### 根因（三处，都跟节拍/时序有关）

1. **端口表是夹在登录检查里发的**。`_publish_port_map()` 只在 `check_login()` 里、
   而且要求页面已经导航到 bing 域才调用；账号又是串行处理的（第 1 个登录 20 秒、
   第 2 个才开始）。所以端口表是「一个一个长出来的」，第 2~4 个账号在自己的条目
   写进去之前就被脚本猫叫醒了。旧脚本每分钟敲门，下一分钟就自愈；**新脚本 20 分钟
   才来一次，一次失败就是一整轮串号**。
2. **「已在运行」被当成「还能用」**。`get_running_pid()` 命中就直接沿用，只额外判断了
   「GUI 模式下别沿用无头实例」一种情况。跨天残留、上次崩溃留下的浏览器，进程活着，
   但登录态/脚本猫后台上下文/cron 挂载都可能已经死了 —— 沿用它等于整轮白跑。
3. **25 分钟的停摆阈值是按「每分钟敲门」定的**。新节拍下，一轮跑满 20 分钟后到下一轮
   开跑之间，正常静默就有 20 分钟（等 cron）+ 最多 5 分钟（轮内错峰）≈ 25 分钟，
   正好压在阈值上。一旦越线，`_stall_repair()` 会去 reload 扩展 —— 那是把**正在跑的
   那一轮**当场掐断，属于「修坏了」。

### 改了什么

| 改动 | 位置 | 说明 |
|---|---|---|
| **新增 `_prepublish_port_map()`** | `_publish_port_map` 之后 | 浏览器一并发拉起就**一次性**把全部账号的「端口 + MUID」写进端口表。每台只开一次 CDP 读 `Network.getCookies` 取 MUID（不导航、不读页面），四台并发、几秒出结果。抢在 cron 第一次敲门（:00/:20/:40）之前完成。单账号不跑（没有串号风险）。`check_login` 里那次发布保留做兜底刷新 |
| **新增 `_proc_age_sec()`** | `get_running_pid` 之后 | 读 `/proc/<pid>/stat` 的 `starttime` 换算进程年龄（标准库，不引 psutil）。不用 profile 目录 mtime —— 浏览器一直在写，mtime 永远是「刚刚」 |
| **沿用前先校验寿命** | `main()` 账号循环 | 年龄 > `BROWSER_MAX_AGE_HOURS`（默认 6 小时，0=不限制）→ 关掉重建，关不干净就 `kill_all_for_profile()`。日志里「已在运行，本次沿用」那行也会带上已运行时长，一眼看出是不是陈旧实例 |
| **停摆阈值 25 → 40 分钟** | 常量区 | 按 20 分钟节拍重算（20 + 5 分钟错峰 + 余量）。想恢复旧值：面板设 `STALL_ALERT_MIN=25` |
| **END 后延迟关浏览器** | `_on_account_done()` | QLREPORT-END 打在每轮汇总里，紧接着还有 `finish()`/状态落盘/「本轮结束」日志。原来立刻关会把这段尾巴切掉，还让 `zy.py` 的轮次忙标记永远停在「忙」。现在等 `SC_CLOSE_DELAY`（默认 20 秒，0=立刻关） |
| **注释/文案对齐新节拍** | 头部说明、`_pre_task_calibrate`、`_no_run_watch` 告警文案 | 说明新脚本不再读计划里的 hold、执行时刻归它自己的 `@crontab` + `Config.winTime`；「每分钟一行 exec script complete」这种过时描述一起改掉。**只改说明，不改逻辑** |

### 怎么验证改对了

看任务日志这五行（按时间顺序）：

1. `🚀 并发拉起 4 个账号的浏览器` 之后紧跟
   `🗺️ 端口表批量预发布完成：4/4 个账号` —— 必须是 **4/4**。
   如果看到 `3/4（其余由登录检查兜底补发）`，说明某台 CDP 没就绪，看后面那行 `🗺️ 端口表已发布：…` 补齐没有。
2. 每台各一行 `🗺️ 端口表已发布：user-xxx → CDP 922X（MUID xxxxxxxx…）`，端口必须 9222/9223/9224/9225 各不相同。
3. 脚本侧对应 `🎯 认领端口：MUID xxxxxxxx… → 账号 user-xxx → CDP 922X`。
   **四台的账号名和端口要一一对上**，不能四台都写 9222。
4. 复用了旧浏览器时：`ℹ️ 账号 xxx 的浏览器已在运行（PID=…，已运行 3.2 小时…），本次沿用`；
   超过 6 小时则是 `⚠️ 账号 xxx 沿用的浏览器已连续运行 7.4 小时（上限 6 小时）→ 关掉重建`。
5. 账号达标时：`✅ 账号 xxx 任务全部完成，关闭浏览器（先等 20 秒让脚本收尾）`，
   20 秒内还应该能看到脚本自己的 `🕒 本轮结束（用时 N 分钟）` —— 这就是那 20 秒买到的东西。

反向检查（不该出现的）：

- `🚨 账号 xxx 脚本已静默 25~39 分钟` —— 不该再报（阈值已到 40，轮间空窗不再算停摆）。
- `⏳ 账号 xxx 正在执行本轮任务，等这一轮跑完再校准（最多等 60 秒…）` 之后紧跟
  `🧩 开跑前校准结束` —— 允许出现，但**不该**频繁：20 分钟节拍下一次运行最多碰到一次。

### 上线注意

## v0.89 · 2026-11-23（修复 MV3 冻结导致的"阅读做到一半被判死回收"）

### 线上现象（用户为什么要改）

2026-11-23 16:23 那轮的日志里，5 个账号先后在同一种位置被截断：
`16:33 进入阅读节点 → 16:42 ♻️ 上一轮（后台）已经 9 分钟没有动静，判定为卡死，已回收运行标记`，

后果：每个账号阅读刚做一半就被清掉运行标记，只能等当天第二个执行点（17:52~17:55）重跑，白丢进度。

### 根因（顺序 bug，v0.87 的探活没覆盖到）

- 敲门入口 `Sched.runOnce()` 在 **② 处（约 12334 行）无条件调用 `reapDeadRound()` → `reap()` → `isBusy()`**，
  判据只有 `max(at, aliveAt)` 是否超过 `RUN_STALE`（8 分钟），**不探活**。
- MV3 后台被冻结时 `setInterval` 心跳（`heartbeat()` 每 20 秒刷 `aliveAt`）一起停摆，
  正在跑的轮次同样会"8 分钟没动静"→ 在下一次敲门的第一步就被当成死轮次回收。
- v0.87 加的 `probeOwnerAlive()`（等 3 个心跳周期约 62 秒，看 `runAlive` 有没有涨）位于
  **⑥a' 补跑判定（约 12470 行）**，比 ② 晚约 136 行。等轮到它时，running 记录早被清成 done，
  探活对象都没了——保护完全失效。

### 改了什么（都在 `microsoft-rewards.user.js`）

- **② 处的 `reapDeadRound()` 加门控**：仅当 `ownerDead === false`（没挂着 running 记录、或心跳新鲜）时才调用；
  粗筛 `ownerDead === true`（疑似上一轮没心跳）时跳过，不在这一步回收。
- 判死统一交给后面的两条"先探活再动手"路径：
  - ⑥a'（空敲门）：`probeOwnerAlive()` 实测还活着 → `ownerDead=false`，不回收不补跑；确实死了才 `resetRoundState()` + 补跑。
  - ⑦（执行点命中）：`isBusy()` + 探活，活着就让路跳过执行点，死了才清标记。
- `ownerDead` 原本就是 finaleCatchup / needMore / 排程跳过 / 开跑前的统一门控，探活活着时置 false 会正确让路，
  不会双开、不会漏执行点。

## v0.87 · 2026-11-23（修复 MV3 冻结导致的「上下文被销毁」误判风暴）

### 线上现象（为什么要改）

2026-11-23 下午四账号实跑，每轮开跑约 5 分钟后必现：

```
♻️ 上一轮跑到一半上下文被销毁（已安静 5 分钟）
🩹 当场补跑（今日第 N/4 次）
```

marvin 一下午烧光 4 次补跑额度，之后只能 `🟡 补跑已用满，等下一个执行点`。

### 根因

存活判据是心跳：任务上下文每 20 秒刷一次 `aliveAt` / `runAlive`。MV3 后台在长
`await`（阅读单次等待可达 3 分钟 `otherSpan` + 网络请求）期间被 Chrome 冻结，
`setInterval` 心跳跟着停。于是「冻着但活着」和「真死了」从外部看一模一样：

1. 粗筛 `RUN_HEARTBEAT_STALE = 4 分钟` 命中 → 判「上下文已死」；
2. 探活 `probeOwnerAlive()` 只等 2 个心跳周期（42 秒），冻结期 `runAlive` 照样不涨 → 误判坐实；
3. 清锁 + 补跑 → 补跑又进阅读长等待 → 又被冻结 → 循环，直到 4 次额度耗尽。

源码注释里 long、Dean 的同类误判早有记录，属已知设计缺陷，v0.87 集中修正。

## v0.82 · 2026-11-22

把 `winTime`（运行时段）的默认值改成 `auto`：**运行时段直接采用 zy.py 计划里的「开机 ~ 收工」**，
不再由脚本自己定死 09:00-23:00。计划读不到时仍退回 09:00-23:00，脚本单独跑也不会半夜乱开。

### 现象

23:12 那次任务：

```
23:12:12 | 📋 任务计划：开机 23:12，收工 23:59；⏸️ 已置「暂缓开跑」…
23:13:04 | [long] 🌙 当前不在运行时段（09:00~23:00，以面板 Config.winTime 为准），本次唤醒不跑任务
23:14:52 | 🧩 开跑前校准结束，放行任务（本次运行不再重复检查）
23:15:00 起 | 每分钟 × 4 个账号：exec script complete —— 一条任务日志都没有
```

zy.py 把收工顺延到 23:59、保持浏览器运行到 23:59，脚本却判定「不在时段」，
浏览器白开 47 分钟、一个任务没做；日志上还看不出来（那句 `🌙` 有 2 小时节流）。

### 根因

`winTime` 是脚本自带的每日闸门（cron 每分钟唤醒 → 窗口外直接 `return`），
它的存在意义是「脚本脱开 zy.py 也能独立跑，别半夜乱开」。
但 zy.py 已经接管了生命周期（随机开机、跑完关浏览器），这道闸门就成了**重复闸门**，
而且默认值 09:00-23:00 会**截断 zy.py 的收工时刻**。

### 改了什么

`zy.js`（13152 行，MD5 `7426c5b8`）· `@version` 0.81 → 0.82

| 改动 | 说明 |
|---|---|
| **`winTime` 默认值 → `auto`** | 面板「运行时段」留空或填 `auto`/`plan` 都等于跟随计划；填具体时段（如 `09:00-23:00`）则完全按你填的来；填 `00:00-00:00` = 全天不限 |
| **新增 `planWin()`** | 只认今天计划的 `startMin~untilMin`；不是今天的、区间异常的（跨天/收工早于开机）一律返回 null → 退回出厂时段 |

2. **一轮结束得太快，判死阈值又太短。** 轮末 `state("done")`，`isBusy()` 用的 `RUN_STALE` 是 2 分钟 → 下一分钟敲门就认为「没有一轮在跑」，直接开新一轮。
3. **每轮都从签入开始跑完整流程。** 没有一个「先盘点、全空就别跑」的闸门，所以哪怕今天全做完了，每轮照样打十几次接口、花 25~40 秒。

对照本地 yh.js：它的 `@crontab` 是每 20 分钟一次，一轮 1~2 分钟，天然就是「20 分钟检查一次」。本脚本是每分钟敲门，就必须自己补一道节拍。

## v0.79 · 2026-11-22

一轮改成**节点式**执行：一个节点只做一种任务（全搜索 / 全阅读 / 其他活动全做完），节点之间停 1~3 分钟随机；每个节点开头先盘点还剩什么，做完的直接跳过；本轮没做完就留续跑标记，下一声敲门接着做，不再干等下一个执行点。

### 现象

`long` 账号 21:17~21:36 那段日志（v0.78 之前的脚本）：

```
🔴 本轮已到 20 分钟上限，每日活动交给下一轮
🟡 阅读到点交班，还剩 8 篇交给下一轮（当前节拍 180 秒）
♻️ 确实停了 / 🔴 运行锁已被其它上下文接管 / ⏳ 另一个上下文正在运行任务
```

20 分钟只涨 3 分。逐条对着时间戳看，是三个问题叠在一起：

1. **一轮只够干一件事，但一轮里塞了十件事。** 一轮 20 分钟硬截断，前面还有 25~40 秒固定开销（出口检测 / 换 Token / 读余额 / 清标签页）。阅读一篇要一个 `otherSpan` 节拍（默认 180 秒），20 分钟理论最多 6 篇，实际只够 2~3 篇；搜索一次要 1~2 分钟，10 次就把窗口吃光。
2. **搜索和阅读混在同一个窗口里抢预算。** 搜索先跑，跑完剩下的几分钟才轮到阅读；阅读又有个自己叠的 8 分钟上限，于是日志里天天是「还剩 8 篇交给下一轮」，一天下来阅读永远差几篇。
3. **每轮无脑重跑所有阶段。** 月度计划、桌面周任务、连签、国际版、领取积分即使当天早就做完了，下一轮照样把所有接口再打一遍——这些请求不产生任何积分，只白占时间、还多一次风控面。

### 改了什么

`zy.js`（0.78 → 0.79，12962 行，MD5 `555e0d4b`）

| 改动 | 说明 |
|---|---|
| **节点式执行**（`runNodes`） | 一个节点 = 一个 20 分钟窗口（沿用原来的轮预算）。节点类型只有三种：`search`（整节点全搜索）、`read`（整节点全阅读）、`other`（其他活动一次全做完）。**搜索和阅读绝不混在同一个节点**——要么整节点都在搜，要么整节点都在读 |

| **搜索不再「分散到全天」** | `spread` 强制关闭：不再按剩余轮数随机分摊、不再整轮跳过。搜索节点就是把 20 分钟全用来搜，搜到配额满或节点到点 |
| **续跑标记**（`Config.needMore`） | 本轮结束时盘点仍有待做、且本轮确实推进过（配额/阅读进度涨了或其他待做项变少），就落一个标记。下一声敲门（1 分钟内）识别到直接开跑，**不占执行点**，30 分钟有效。18 点前也不用干等下一个执行点 |

| **汇总口径** | 每日活动没进 other 节点（盘点判定已完成）也算达标，否则「今天早做完了」会被算成差一项、每轮白跑一遍 |

### 和计划（执行点）的关系

计划**没有被绕过**，仍然负责三件事：几点开机（`startAt`）、几点收工（`untilMin`）、在「开机 + 5 分钟 ~ min(收工-10, 18:00)」之间撒执行点。**撒点参数同步改成了「一轮的长度」**：间隔 70 分钟、点数 3~9（9:00~18:00 约 8 个，13:00 才开机约 5 个，只剩一个多小时则 2 个），点与点首尾相接。改的是「点有多密」+「命中一个点之后跑多久」：

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 命中普通执行点 | 硬跑 20 分钟，到点截断，剩下的交给 15 分钟后的下一个点 | 命中后进入节点循环，最多连续跑 60 分钟（3 个 20 分钟节点 + 2 次 1~3 分钟间隔），做到盘点为空才停 |
| 循环期间撞上后面的执行点 | —— | 该点被 `hitWakePoint` 标记已用并在日志里让路（`上一轮还在执行中…本分钟静默让路`）。**执行点变成「最晚开工时刻」，不是「必须单独跑一轮」**。间隔拉到 70 分钟后这种让路从「每轮撞 3~4 次」降到「偶尔撞 1 次」 |
| 本轮没做完 | 干等下一个执行点（可能几十分钟） | 落 `Config.needMore` 续跑标记，下一声敲门（1 分钟内）直接接，不占执行点，30 分钟有效 |
| 当天最后一个执行点 | 预算放宽到「离收工还剩多久」（最多 45 分钟） | 同一套放宽逻辑保留，上限提到 **60 分钟**（= 一串节点），另外节点循环本身还会被 `untilMin` 夹住，不会跑过收工线 |
| 18:00 之后 | 计划不排点，脚本不动（等不到命中） | `todayPlan` 直接返回 `mode:"continuous"`，`hitWakePoint` 每次敲门都放行 → 一轮接一轮做到今天做完；18 点后**第一次**敲门先等 3 分钟避开 zy.py 的扩展校准 |
| 计划接口读不到 | 回退到上午/下午/全天的固定区间 | 同样回退（起点改为「本账号实际启动时刻」，上界仍是 18:00），不受节点化影响 |

一句话：**执行点决定「最晚什么时候可以开跑」，节点数决定「一次跑多久」**。两者都按「一轮 ≈ 60 分钟」对齐，所以计划表上一天 8 个点左右、实际是 8 段连续的作业时间，中间只隔 10 分钟收尾余量。不要为了多跑而加执行点 —— 加点是没用的，点多只会在循环里被让路。

新增面板配置（`Config`）：

| 键 | 默认 | 作用 |
|---|---|---|
| `nodeGapMin` | 60 | 节点间隔最小值（秒） |
| `nodeGapMax` | 180 | 节点间隔最大值（秒），与最小值之间随机取 |
| `spread` | false | 节点模式下不生效，保留只为兼容旧配置 |

1. **一进来就有盘点**（以前没有）：

## v0.78 · 2026-11-22（仅 zy.py / sc_deploy.py）

扩展版本判断改成**跟线上最新版比**，不再拿磁盘里那份当标尺；落后时走 GitHub 加速站下载官方包，覆盖解包目录后 reload。`zy.js` 不变（仍是 0.78）。

### 现象

```
2026-11-22 21:19:28,487 | INFO |   🔎 账号 marvin 脚本猫扩展已是最新 v1.4.0
2026-11-22 21:19:28,489 | INFO |   🔎 账号 long 脚本猫扩展已是最新 v1.4.0
2026-11-22 21:19:28,494 | INFO |   🔎 账号 joe 脚本猫扩展已是最新 v1.4.0
2026-11-22 21:19:28,495 | INFO |   🔎 账号 Dean 脚本猫扩展已是最新 v1.4.0
```

而线上最新是 **v1.5.2**。日志说「已是最新」，实际落后两个版本。

### 根因：判断标尺选错了

旧 `ensure_ext_current()` 只做一件事——比对「浏览器里已装版本」和「磁盘解包目录 manifest 里的版本」：

```python
if disk:                      # 容器镜像自带 /app/extensions/scriptcat，manifest 写着 1.4.0
    if dt <= bt:              # 1.4.0 <= 1.4.0  → 成立
        res["ok"] = True
        return res            # 直接返回，日志打「已是最新」
```

镜像里那份解包目录本身就是 1.4.0，已装也是 1.4.0，两个 1.4.0 相比自然相等 → **永远得出「已是最新」**。它从头到尾没问过「线上是多少」。

更关键的是：容器里装的 `eflkdikabffkjhhndpmlggcgiifnjbdk` 是**解包扩展**（ID 由目录路径哈希算出），manifest 里没有 `update_url`，`chrome.developerPrivate.autoUpdate` 对它**无效**——点「更新」什么也不会发生。所以只要磁盘目录不换，扩展就永远停在 1.4.0。

### 改了什么

`sc_deploy.py`

| 新增 | 作用 |
|---|---|
| `ext_latest()` | 去 GitHub Releases 查脚本猫最新版（`scriptscat/scriptcat`），拿到版本号 + `scriptcat-<ver>-chrome.zip` 下载地址。进程内 + 落盘缓存 30 分钟，4 个账号共用一次查询；网络失败时退回过期缓存并标 `stale` |
| `_ver_cmp()` | 版本比较，`1.4` 与 `1.4.0` 视为相等（旧代码用元组直接比会误判） |
| `_download_file()` | **GitHub 加速站优先**：默认按 `ghfast.top` → `ghproxy.net` → `gh-proxy.com` → 直连 的顺序试，任一个失败换下一个；下载完校验是不是真 zip（防加速站返回错误页） |
| `_shared_pkg()` | 同一进程 4 个账号共用一个安装包：第一个下载，其余等它下完直接用（否则 4 份 5MB 并发下载既慢又容易被加速站限流） |
| `install_ext_zip()` | 下载官方 zip → 校验包内 manifest 版本 == 线上版本 → 解到 `<目录>.new` → 旧目录改名 `.bak-<时间戳>` → 新目录就位。任一步失败回滚，原目录不动 |
| `_wait_ext_version()` | reload / 商店更新后轮询等版本落定（Chrome 更新是异步的，立刻读常常还是旧值） |

`ensure_ext_current()` 重写为三态判定：

| 情况 | 动作 | 日志 |
|---|---|---|
| 已装 < 线上最新 | 覆盖解包目录 + reload；解包通道不通则点商店更新并等 20 秒 | `⬆️ 扩展已更新 v1.4.0 → v1.5.2` |
| 已装 ≥ 线上最新 | 才算最新（磁盘目录若更高仍 reload） | `🔎 已是最新 v1.5.2（线上最新 v1.5.2）` |
| 线上版本查不到 | 只做磁盘比对，`verified=False` | `⚠️ 线上最新版未取到，本次无法判断是否最新` |

第三种情况是重点：**查不到就不许下结论**，不再有「假的最新」。

`zy.py`

- `_ensure_ext_latest()` 按上表四态打日志，落后且升级失败时打 `⚠️ 扩展落后：已装 v1.4.0 < 线上最新 v1.5.2`，不再含糊成「已是最新」。
- 扩展换版后补一次「允许用户脚本」+「静默更新非重大变更」，再等 4 秒读脚本——跨版本升级可能重置 Chrome 侧的开关，不补的话脚本会读不到。
- `--update-ext` 传 `force_latest=True`，手动更新不吃缓存。

新增环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `SC_EXT_REPO` | `scriptscat/scriptcat` | 版本来源仓库 |
| `SC_EXT_MIRROR` | `https://ghfast.top/,https://ghproxy.net/,https://gh-proxy.com/` | GitHub 加速站，逗号分隔按顺序试；置空或 `off` 只直连 |
| `SC_EXT_AUTOINSTALL` | `1` | 落后时自动下载覆盖；`0` 只报告不动手 |
| `SC_EXT_LATEST_TTL` | `1800` | 线上版本查询缓存秒数 |

### ⚠️ 一个前提：解包目录要可写

覆盖扩展目录需要写权限。容器里 `/app/extensions/...` 若是只读挂载，升级会**如实失败**（原目录保持不动，日志写「扩展目录所在路径不可写…把 SC_EXT_DIR 指到可写目录」）。这时把 `SC_EXT_DIR` 指到 `/data` 下的可写目录即可。

首次升级会保留一份备份 `scriptcat.bak-<时间戳>`（只留最近一份），确认没问题后可自行删除。

用户要求：**18 点之后不用计划、直接按默认一直做，做到做完；计划不排 18 点后。**

现在把 18:00 当作「计划模式的终点」：18 点前照旧（计划/回退 + 随机撒点，反检测行为不变），18 点后不再有点，敲门即跑，靠运行锁保证「一轮跑完再下一轮」。

## v0.76 · 2026-11-22

修一个把整晚排程带偏的解析 bug：**收工时刻顺延到「次日 00:00」时，计划被判成「区间太窄」整份丢弃**，于是脚本沿用上一次会话的旧开机时刻，连带着 `hold` 闸门一起失效。

### 改了什么

| 位置 | 旧行为 | 新行为 |
|---|---|---|
| `zy.js` 解析计划 | `runUntil` 只取「时:分」，次日 `00:00` 解析成 0，比开机 20:58 还小 → 判「区间太窄」→ 丢弃 | 收工分钟 ≤ 开机分钟 = 跨天，按「今天 23:59 收工」处理，区间正常撒点 |
| `zy.js` 读不到计划的日志 | 只写「沿用本会话缓存的开机时刻 20:09」——既没原因，措辞也不对（那是**上一次会话**的） | 带失败原因：「本次读不到 zy.py 计划（计划写入于 20:09，早于本次浏览器启动 20:58 → 上一次会话的旧计划），沿用上次读到的计划：开机 20:09 → 收工 00:00」，10 分钟节流 |
| `zy.js` 计划新鲜度 | 只卡「20 小时内」 | 再卡一条：计划写入时刻早于本次浏览器启动 5 分钟以上 → 判为上一轮残留，丢弃 |
| `zy.js` 缓存复用 | 要求 `bootId` 相同，而 `bootId` 是 `performance.timeOrigin`，**脚本猫每次敲门都是新上下文，这个值每次都变** → 每分钟都重拉一次计划 | 跨上下文时改为「每 3 分钟允许复核一次开机时刻」，复核记录落盘（`Config.planTryAt`），不再是内存变量 |
| `zy.js` hold 查询节流 | 15 秒内存节流，跨上下文等于没有 | 落盘节流 30 秒（`Config.holdTryAt`） |
| `zy.py` 扩展校准 | `sc_deploy.py` 缺函数时 `return False`，调用方 `.get("changed")` → 4 条 `AttributeError: 'bool' object has no attribute 'get'` | 返回同形状 dict，并兼容旧版返回 bool |
| `zy.py` 计划自检 | 只验「能读到 JSON」 | 比对内容里的 `startAt`：端口上是上一轮残留实例时应答时当场告警，不再假通过 |

### 为什么改

线上 20:58 启动、`BING_RUN_SECONDS=36000` 超出当日剩余时间，zy.py 按「跑完再结束」把收工顺延到 **次日 00:00**：

```
2026-11-22 20:58:37 | 📋 任务计划：开机 20:58，收工 00:00；⏸️ 已置「暂缓开跑」（900 秒内失效）
2026-11-22 20:58:37 | ✅ 计划自检通过：脚本猫可从 http://127.0.0.1:47831/zy-run-plan.json 读取
[20:59:06] [long] 📋 本次读不到 zy.py 计划文件，沿用本会话缓存的开机时刻 20:09
[21:00:00] [long] 📋 本次读不到 zy.py 计划文件，沿用本会话缓存的开机时刻 20:09   ← 54 秒后又说一次
[21:00:10] [long] ⏰ 定时唤醒：开始本轮任务                                ← 开跑了
2026-11-22 21:00:22 | 🧩 开跑前版本校准（脚本猫首轮心跳已到）              ← 校准才开始
```

三个问题串成一条链：

1. **解析**：`runUntil="2026-11-23T00:00:00"` 取到的分钟数是 0，`hi = 0-30 = -30`，`hi-lo < 1` → `_planErr="计划区间太窄（20:58~00:00，已过收工？）"` → 整份计划被丢弃。**只要收工跨天就必然触发**，与账号无关。
2. **兜底**：丢弃后沿用缓存里的旧计划（20:09 开机，来自当天早些时候那一轮）。旧区间把执行点撒在 20:14 之后，21:00 正好命中 → 开跑。
3. **闸门失效**：`hold` 是写在计划文件里的，计划读不到 = `hold` 读不到。于是 zy.py 20:58 置的「暂缓开跑」完全没生效，脚本 21:00:10 开跑、zy.py 21:00:22 才开始校准 —— v0.75 想避免的「校准掐断正在跑的那一轮」又出现了。

顺带两个噪音/隐患：`bootId` 拿 `performance.timeOrigin`，脚本猫的后台执行上下文每次敲门都是新建的，所以「同会话」判断永远不成立，每分钟重拉一次计划，失败就刷一条日志（20:59:06 与 21:00:00 两条同因）；`sc_deploy.py` 版本过旧时 `_ensure_ext_latest` 返回 `False`，调用方当 dict 用，4 个账号各抛一次 `AttributeError`。

| `zy.py` | 4,271 | `80313b79` |

### 怎么验证改对了

- 读计划成功时，日志会明确写收工跨天：
  `📋 已读取 zy.py 计划（http://127.0.0.1:47831/zy-run-plan.json）：开机 20:58 → 收工 23:59（收工在次日，按今日 23:59 收工），执行点撒在 21:03~23:29`

| `zy.py` 写计划 | 写完就让脚本随便跑 | 需要校准时先置 `hold=true`，校准结束（成功/失败/跳过都算）立刻置回 `false` |
| `zy.py` 校准时机 | 等「脚本猫首轮心跳」→ 但首轮心跳往往就是**开跑那一轮** | 先等「所有账号这一轮都跑完」（`SC_CALIB_ROUND_WAIT`，默认 300 秒），有轮次在跑就等，等不到就跳过本次校准 |
| `zy.js` 开跑判定 | 到点就跑 | 到点先查 `hold`：还被拦着就 `⏸️` 打一条、保留执行点，绝不半路被校准掐断 |
| 扩展校准 | 直接调 `ensure_ext_current`，旧版 sc_deploy.py 会抛 AttributeError | 缺函数时给一句明确提示「请把新版 sc_deploy.py 一起上传」，不再刷 4 条异常 |

### 为什么改

线上 20:44 那次启动的日志：

```
[20:45:02] [long] 🚀 启动全能自动化任务...        ← 已经开始跑任务
2026-11-22 20:46:16 | 🧩 开跑前版本校准（脚本猫首轮心跳已到）
2026-11-22 20:46:43 | [long] install success      ← 脚本被替换，这一轮当场没了
```

「首轮心跳」这个信号其实是脚本每分钟的例行敲门，而 long 20:45 正好是执行点，于是它先开跑、再被校准打断，20:45 那一轮的搜索/阅读全部白丢。同一份日志里还有 4 条 `module 'sc_deploy' has no attribute 'ensure_ext_current'` —— 容器里的 `sc_deploy.py` 还是旧的，扩展校准根本没执行。

改完之后顺序是：

```
写计划（hold=true）→ 脚本敲门只打心跳、不开跑
  → zy.py 等首轮心跳 + 等所有账号这一轮跑完
  → 一次性校准（扩展 + 脚本）
  → 放行（hold=false）
  → 脚本下一个敲门立刻开跑
```

### 怎么验证改对了

1. 启动阶段：`📋 任务计划：… ；⏸️ 已置「暂缓开跑」（900 秒内失效）`；

## v0.74 · 2026-11-22

修「空敲门把还在跑的那一轮判死」：判死（探活 42 秒 + 清锁清缓存）从「每分钟的例行检查」挪到「确实要开跑的那一刻」。

### 改了什么

| 位置 | 旧行为 | 新行为 |
|---|---|---|
| 每次敲门开头 | 心跳超 4 分钟就**当场**探活 42 秒，判定死了就 `resetRoundState`（清运行锁 + 6 项缓存），再报「补跑已用满」 | 只做粗筛标记，**不探活、不清锁、不打日志** |
| 补跑判定 | 在读排程之前无条件判定，非执行点也会触发 | 挪到排程门控之后，只在「非执行点 + 粗筛命中」时探活确认；探活活着就什么都不做 |
| 探活结论 | 只有一次 42 秒判断 | 探活后再拿时间戳复核：1 分钟内还有活动就按「仍在跑」处理（与让路判断同一口径） |
| 换会话（重启/重新启用/睡很久） | 之后仍可能按「上一轮被打断」再补跑一次 | 直接视为新会话从干净状态开跑，不再白烧补跑额度 |
| 探活耗时后的时间 | 用探活前的时刻算排程 | 探活后重算 `now` 并重算执行点，避免漏掉刚过点的执行点 |

### 为什么改

线上 20:34 的日志：

```
[20:34:42] [long] ♻️ 新会话（上一轮跑到一半上下文被销毁）：运行锁与缓存已重置（已清理 6 项运行缓存）
[20:34:42] [long] 🟡 上一轮跑到一半被打断，但今日补跑已用满 4 次，等下一个执行点
```

20:31 是 long 的执行点，20:34 只是每分钟例行的空敲门。空敲门却做了两件重活：先花 42 秒探活，判定「死了」就把那一轮仍在使用的锁和缓存全清掉，然后因为当天补跑额度已满，直接放弃。

后果有三层：
1. 若那一轮其实还在跑（MV3 后台被冻结时心跳会一起停，时间戳看着就像死了），锁被清掉等于让它和后来的上下文抢同一把锁；
2. 每天都在非执行点上做多次 42 秒探活，白等；
3. 日志里的「补跑已用满」出现在一个根本没有执行点的时刻，看着像任务被放弃了。

| 文件 | 行数 | MD5（前 8 位） |
|---|---|---|
| `zy.js` | 12,328 | `54bf4624`（`@version` 0.73 → **0.74**） |

`zy.py` / `sc_deploy.py` 本轮未改。

### 怎么验证改对了

1. 非执行点的敲门不再出现 `♻️ 新会话（上一轮跑到一半上下文被销毁）`，也不再出现「补跑已用满 X 次，等下一个执行点」；
2. 真被打断时，日志顺序变成「先确认、再补跑」：`♻️ 上一轮跑到一半上下文被销毁（已安静 N 分钟）…` 紧接 `🩹 上一轮跑到一半被打断，当场补跑（今日第 1/4 次，不占执行点）`；
3. 上一轮还在跑时（后台被冻结后解冻），空敲门应当**什么日志都没有**，下一个执行点仍正常开跑。

## v0.73+ · 2026-11-22（仅 zy.py / sc_deploy.py）

改版本校准的时机：启动时正常启动，只在任务正式开跑前校准一次；同时把脚本猫扩展插件本身的更新也纳入。

### 改了什么

| 项 | 旧行为 | 新行为 |
|---|---|---|
| 校准时机 | 每个账号浏览器刚拉起就比对版本，落后立刻更新 | **启动阶段只确保扩展/脚本「在、已启用、已授权」**；等所有账号就绪、脚本猫首轮心跳出现（脚本已读计划、任务还没开跑）后，**统一校准一次** |
| 校准次数 | 每个账号各查一遍（4 个账号 4 次） | 全进程**只做一次**（`_CALIBRATED` 标记），4 个账号并行 |
| 校准范围 | 只校准签到脚本 | 签到脚本 **+ 脚本猫扩展插件本身** |
| 等不到心跳 | — | 按 `SC_CALIB_WAIT_SEC`（默认 180 秒）兜底校准，仍然只做一次 |
| 浏览器开关 | — | 全程**只 reload 扩展、不重启浏览器**，同路径扩展 ID 不变，脚本与 Cookie 授权都保留 |
| 手动更新 | `--update-script` / `--install-script` | 新增 `--update-ext`：单独更新扩展插件（浏览器没跑会临时拉起，完成自动关） |

### 为什么改

- 原来每个账号一启动就比对版本，落后就 reload。reload 会重建脚本猫后台 SW，脚本把这一刻当成「新会话」（日志里 `♻️ 新会话（浏览器重启过）`、`🔑 首次运行：请求 Cookie 读取权限` 就是它引起的），等于任务还没开始就先被重置一次。
- 4 个账号各查一遍也意味着 4 次重复的扩展页探测和版本请求，日志看着像反复打开浏览器。
- 更合理的时机：脚本猫首轮心跳出现时扩展已经加载完、脚本已经读完计划，但还没到执行点 —— 这时校准既不会漏掉落后版本，也不会打断正在跑的任务轮次。
- 扩展插件此前完全没有更新通道：面板换了新扩展目录也不会生效，只能靠重建 profile。
