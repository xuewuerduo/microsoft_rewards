# 参考脚本 #8787 解读 + 回归方案

> 对象：脚本猫商店 <https://scriptcat.org/zh-CN/script-show-page/8787>，作者源仓库 `github.com/hidmould/MicrosoftPoints`
> 取样版本：**v1.5.9**，10823 行，MD5 `64ae3c81`
> 我方对照版本：`microsoft-rewards.user.js` **v0.90**（13272 行）
> 本文只讲"它怎么设计、我们偏在哪、怎么回去"，不贴大段代码。

---

## 一、一句话概括

参考脚本是**"每 20 分钟被 cron 叫醒一次、跑一轮、跑完退出"**的定时任务，不是常驻进程。
整个设计的支点是元数据里的 `@crontab */20 * * * *`——脚本内部**没有**"到没到点"的第二层判断，也没有常驻循环。

我方脚本是**"每分钟叫醒一次"**，于是不得不在内部补一层"执行点/撒点/连续模式/补跑"来防止重复执行和空转。
两者复杂度差距的根源就在这一行 crontab。

---

## 二、五条核心模型

1. **一次唤醒 = 一轮**。`Sched.runOnce()` 是唯一入口（`10415` 行），返回的 Promise 就是"这一轮结束"，跑完上下文销毁。
2. **单轮预算 20 分钟**，硬上限 40 分钟（`ROUND_BUDGET_MS` 7939、`ROUND_HARD_LIMIT` 10132）。超时任务不是补跑，只打一句「本轮已到 20 分钟上限，交给下一轮」（9341），20 分钟后 cron 自然再来。
3. **运行时段由脚本判断，crontab 写死全天**（`Config.winTime` 默认 09:00~23:00，10135）。注释写明了理由（10088）：cron 写在元数据里，写 9-23 会和面板配置错位。
4. **没有执行点、没有撒点、没有补跑**。20 分钟周期本身就是节拍。
5. **只有后台上下文跑任务**。页面上下文只做代发接口、菜单、授权。

---

## 三、一轮的生命周期（runOnce 八个步骤）

| 步骤 | 位置 | 做什么 |
|---|---|---|
| ① 会话判定 | 10419~10460 | bootId 变了 / 离开 >30min / 非 cron 刻度（±2min）/ 上一轮 owner 已死 / 刚重载 <90s → 任一命中就清锁、清认领、清缓存，本轮从头开始 |
| ①b 跨天 | 10462~10471 | 日期变了同样清痕迹（今日进度各带 date 字段，不受影响） |
| ② 清理 | 10473~10495 | 回收真死的轮次、清超时未开始的认领、清孤儿锁（锁 TTL 6 分钟） |
| ③ 时段闸门 | 10481~10505 | 不在 `winTime` → 写 waiting 直接退出，2 小时才打一条日志 |
| ④ 已完成 | 10511 | `keep` 关着且今天已完成 → done，不再跑 |
| ⑤ 搜索冷却 | — | 冷却到期自动重置 |
| ⑥ 并发闸门 | 10528 | `isBusy` → `probeOwnerAlive()` 实测心跳（2 个心跳周期 + 2 秒，约 42 秒）；活着就跳过，死了就 reset |
| ⑦ 错峰 | — | 随机等 0~5 分钟，躲开整点 |
| ⑧ 干活 | — | 认领 → `init()` → `runAll()` → `finish()` |

`runAll()`（9181）的顺序固定，每个阶段都套一层 `withRetry`（失败重试 2 次，间隔 60 秒）：
签到 → 阅读 → 桌面周任务 → 月度计划 → 活动卡片 → 搜索 → 连签 → 每日活动 → 国际版 → 领积分 → 二次扫描 → Edge → CDP 收尾 → 汇总。
**没有节点分组，没有节点间 1~3 分钟停顿。**

## 五、我们偏离了哪三处（这是慢和空转的直接原因）

### 1. 节拍从 60 秒级变成 0~180 秒真随机

参考脚本的 `SEARCH_PACER`（7941）写得很直白：`SPAN_MIN_MS = 60 秒`、`JITTER_MS = ±15 秒`，配 60 就是 45~75 秒；
`nextGap()` 注释是「不再退让：无论上一轮是否记账，下一次都用同一个基准间隔」。

我们 v0.88 把它改成 0~180 秒真随机、还加了 10% 概率的 5 分钟长等待。结果是搜索 60 次的理论耗时从约 60~75 分钟
变成动辄 2 小时以上。日志里 `间隔 0~120 秒真随机`、`每篇约 3 分` 那些行就是这套逻辑。

### 2. 阅读从"还差几篇读几篇"变成"按剩余执行点摊派"

参考 `doRead`（8373）：

```
target = min( max( ceil((max - cur) / 3), 1 ), 10 )
```

就是"还差几篇读几篇（上限 10）"，配合 8 分钟 `readCap` 和 20 分钟轮预算，一轮能推进一大截。

我们 v0.88 加了 `pickShare()`（8277）：先给后面每轮各留 1 次，本轮按 `avg × factor` 抽一个小份。
在"每分钟叫醒"的前提下这是防重复的必要手段，但代价是**每轮只读 1~2 篇**。
日志里 marvin 一小时 21/30 → 24/30、每轮 `本轮读 1 篇`，根子就在这。

### 3. DAPI 重试丢了

参考 `readProgressWithRetry(3)`（8448）：读不到就 3.2 秒后重试，最多 3 次，然后才判失败。

我们 `API.getReadProgress()`（3590）读不到就打一行 `DAPI 响应不是 JSON: null` 直接 `return false`；
任务列表同理（3734）。日志里 `DAPI 响应不是 JSON: null` → `阅读进度查询失败` → 盘点失真 → 空转判断不准，
这一条链每轮都在 marvin 身上重演。

## 六、还有一处被误读：Edge 连签不是"本轮任务"

参考脚本里 Edge 在 `EdgePacer`（7908），**挂在轮的 20 秒心跳定时器里**（8095~8106）：

- 心跳每次 tick 调一次 `maybeReport()`，`busy` 防重入；
- 按服务端给的 `intervalMin`（默认 5 分钟）节流，`done` 之后 `nextAt = now + 30 分钟`；
- 上报次数、总量、开始时间全部持久化在 state 里，**跨轮累计**，一天内自然凑满。

注释原话：「只在『本轮执行』期间上报，EdgePacer 自按 intervalMin 节流，一轮 20 分钟推进 3~4 次。」

我们的做法是把它当成本轮必须做完的任务放进节点，串行等 30 分钟。可一轮只有 8~10 分钟，
必然被打断、计数丢失、重来。marvin-1 第一轮就 `达标 5/6` 提前收尾、Edge 只报 1/6，后面补跑轮次也接不上，
最终 0/30——这不是"任务没做完"，是**模型用错了**。

## 七、我方多出来的东西（以及它们的真实成本）

| 我们加的 | 起因 | 代价 |
|---|---|---|
| 执行点 / 撒点 / `planRaw` | 每分钟 cron，必须判断"现在该不该跑" | 需读 zy.py 计划文件；计划读不到就得回退，回退逻辑本身又是一层 |
| 连续模式（18 点后 20 分钟节拍） | 计划不排 18 点后，只能靠"上一轮结束 +20 分钟" | 与 cron 每分钟敲门叠加，产生大量 `未命中执行点` 空转日志 |
| 补跑 / 收官补跑 | 达标判定把 Edge 之类长任务排除在"完成"外 | 3 轮补跑额度，且每轮都可能被锁挡掉 |
| 节点分组 + 节点间隔 60~180 秒 | 模仿人类行为节奏 | 与 20 分钟轮预算抢时间，阅读被切碎 |
| `pickShare()` 分批 | 把当天总量摊到剩余执行点 | 晚启动时每轮只做 1 次，赶不上收工 |
| 锁 TTL 加到 10 分钟 | v0.87 修 MV3 后台冻结被误判"上下文已死" | **直接导致"锁 500~590 秒前更新 → 本次跳过"刷屏**，marvin/joe 大半轮次被挡 |

最后一行值得单独说：参考脚本锁 TTL 是 6 分钟、判死 90 秒，靠的是 `probeOwnerAlive()` **实测心跳**
（等 2 个心跳周期 + 2 秒）而不是靠时间戳猜。我们为了躲 MV3 冻结把三个阈值一起放长，
治好了"误判死"，却换来了"该死的不死、轮次被挡"。正确解法是学它：**判死前先探活，而不是把判死时间调长**。

## 八、回归方案（三阶段，可独立上线）

### 阶段 A：参数回归（只改脚本内部，不动调度骨架，风险最低）

| 改什么 | 怎么改 | 预期 |
|---|---|---|
| 搜索/阅读节拍 | `spanMs()` 默认 180 → **60**，抖动改 ±15 秒（45~75），去掉 10% 的 5 分钟长等待 | 搜索 60 次从 2 小时+ 回到约 1 小时 |
| 阅读份额 | 连续模式/最后一轮走"还差几篇读几篇（上限 10）"；有多个执行点时才用 `pickShare()` | marvin 那类 21→24 一小时的情况消失 |
| DAPI 重试 | `getReadProgress()` 外面包 3 次重试 × 3.2 秒；`DAPI 任务列表非 JSON` 同样处理 | 盘点失真大幅减少，空转判断恢复可信 |
| Edge 模型 | 从节点里移出，改成"按 intervalMin 节流、跨轮累计"，满 6/6 打今日完成标记 | marvin-1 不再 5/6 提前收尾、不再重复累计 |

阶段 A 不需要改 `@crontab`，也不依赖 zy.py，改完发一版（v0.91）就能验证。
其中"Edge 改模型"是行为改动里最大的一处，若想稳妥，可拆成 v0.91（节拍+份额+DAPI）和 v0.92（Edge）。

### 阶段 B：骨架回归（改 crontab 与调度主体）

1. `@crontab` 改 `*/20 * * * *`；运行时段判断只留 `winTime` 一层。
2. 删掉执行点/撒点/`planRaw`/连续模式/补跑，`runOnce` 回到"醒来 → 判断能不能跑 → 跑一轮 → 退出"。
3. 并发闸门改成"先探活再判死"：`isBusy` 时等 2 个心跳周期（约 42 秒）实测心跳，活着才跳过。
   锁 TTL 相应回到 **6 分钟**，判死阈值可保留 8 分钟（MV3 冻结的余量），但**不再靠时间戳直接判死**。

代价与注意点（必须提前接受）：

- **启动延迟**：cron 落在 :00/:20/:40，zy.py 09:07 拉起浏览器，首轮要等到 09:20。
  解法二选一：① zy.py 在启动时对齐 cron 刻度（提前到 :58/:18/:38 起浏览器）；② 接受最多 20 分钟空窗。
- **收工尾巴**：最后一轮跑完到下次 tick 之间同样可能空 20 分钟，靠 zy.py 的"全账号完成即关浏览器"兜住，不影响结果。
- **5 账号错峰**：参考脚本的 ⑦ 随机等 0~5 分钟要保留，但建议上限降到 3 分钟，否则实际周期被拉到 23~25 分钟。
- **zy.py 的 hold/暂缓开跑**：20 分钟周期下冲突概率很低（校准通常 1~3 分钟），hold 可以保留做兜底，也可以删掉简化。

### 阶段 C：清理与配套

- 删死代码：`planRaw`、`ensureRunPlan`、连续模式分支、`pickShare` 的执行点耦合、`sc_diag.py` 里查执行点的部分（或改写为查轮次）。
- `zy.py`：① 复用浏览器前校验运行时长（超 6 小时重启，解决 joe 掉登录的疑点）；② 端口表批量预发布（解决 joe 首轮 `端口表里没有本机 MUID`）。
- 发版时按项目约定补 `CHANGELOG.md` 与 `release-notes/`。

## 九、不建议照搬的部分

- **90 秒判死**：MV3 后台会冻结，90 秒在容器里几乎必然误判。我们 v0.87 踩过这个坑，别回退。
  要学的是"探活"，不是"缩短判死时间"。
- **crontab 写死全天 + 面板 `winTime`**：我们的运行时段来自 zy.py 写的计划文件（47831 端口），
  这是多账号容器环境下的额外信息源，比面板手填更准，保留。
- **`Config.span` 让用户自己填**：我们多账号共用一份配置，改一个值影响 5 个账号，默认值给对更重要，配置项可以留但不该是主要调节手段。

---

## 十、建议顺序

1. **先做阶段 A**（v0.91）：节拍、阅读份额、DAPI 重试。这三处是纯收益，不改骨架，出问题好回退。
2. 观察 1~2 天日志，确认搜索/阅读能按预期收口、`DAPI null` 显著减少。
3. **再做 Edge 模型改造**（v0.92），单独一版，便于定位。
4. **最后做阶段 B + C**（v0.93 起步）：crontab 换 `*/20`、砍掉执行点体系、zy.py 两处配套。
   这一步改动面最大，但砍完之后脚本会短很多、日志会干净很多。

如果只允许做一件事：**先改节拍（60±15）**。它是"慢"的最大单一来源，改动最小，效果最直接。
